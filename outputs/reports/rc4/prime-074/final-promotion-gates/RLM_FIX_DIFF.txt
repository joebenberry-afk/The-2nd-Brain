## What does NOT work (tried, rejected, evidence kept)

1. **Renaming the whole venv directory aside before rebuilding** (`rename(venv,
   venv + ".stale-...")`) -- fails with the SAME class of error, just on `rename`
   instead of `unlink`:
   `EPERM: operation not permitted, rename '...\venvA' -> '...\venvA.stale-...'`.
   Windows refuses to rename a directory containing an open-handle descendant file in
   this environment, so this "obvious" fix does not actually work. (raw:
   `raw/fix-attempt-1..3.log`, all FAIL)
2. **Renaming only the specific locked file in place, then retrying `rm(venv, ...)`**
   -- the retried recursive delete still tries to delete the renamed file (same open
   handle, new name, still inside the tree being deleted) and fails identically, just
   with an extra `.stale-...` suffix each time:
   `EPERM: operation not permitted, unlink '...python.exe.stale-...'`. (raw:
   `raw/fixv2-attempt-1..3.log`, all FAIL)

## What works (validated, this is the recommended candidate fix)

Move the one specifically-locked file (identified from `error.path` on the caught
`EPERM`/`EBUSY`) **entirely out of the venv directory tree**, into an OS temp staging
directory (`os.tmpdir()/prime-agent-kernel-venv-stale/`), THEN retry the recursive
delete of the (now-unobstructed) venv, then proceed to the normal rebuild. See the diff
below.

Validation (two independent fresh-venv trials, holder process alive throughout,
identity mutated before each attempt -- the exact collision from RLM_EPERM_REPRO.md):

- Trial 1: attempt 1 succeeded outright; attempts 2-3 succeeded. 3/3 clean.
- Trial 2: attempt 1 hit a DIFFERENT, unrelated, pre-existing Windows transient-lock
  issue (`EPERM ... rmdir '...\Lib\site-packages\jedi\...\tensorflow\tensorflow'` /
  in trial 3 `...\Lib\site-packages\scipy\stats`) -- a known separate class of Windows
  issue (a freshly-extracted-file scan/index lock, most likely Windows Defender
  real-time scanning a just-written large third-party package tree; this is exactly
  the "antivirus/Defender interception" item on the plan's own Phase F checklist, and
  is NOT the target defect: it happens on the FIRST rebuild of a brand-new venv,
  independent of any holder process, and self-resolved on retry). Attempts 2-3
  succeeded cleanly. Net: 2/3 clean immediately, the 1 miss is an orthogonal,
  self-healing, already-known-category Windows issue, not a fix regression.
- In both trials, the target defect (the original holder-process EPERM) never
  recurred once the fix was in place; every failure surface changed to the unrelated
  AV-scan class, and every retry (a real subsequent RLM spawn would naturally retry or
  the AV scan completes) succeeded.

Raw logs: `raw/fixv3-attempt-1..3.log`, `raw/fixv3b-attempt-1..3.log`,
`raw/fixv3b-build.log`.

## Why this fix is NOT being applied to the live install in this pass

1. The plan's own hard constraint (Phase M5): live promotion may only apply "the same
   validated Windows patches" -- i.e. the 2 patches already qualified across three
   independent reviewing passes (`bootstrap.ts` Scripts/python.exe path fix,
   `session-lease.ts` EPERM-as-lease-conflict handling). A brand-new 3rd patch,
   invented and isolation-validated in a single pass, has not been through that same
   standard of scrutiny and would expand this task's scope beyond "close the two
   remaining gates."
2. The actual release-gate pass criterion (Phase I/J: "3 consecutive successful fresh
   spawns") is a STEADY-STATE test -- no concurrent identity-changing event. The
   environment matrix (RLM_ENVIRONMENT_MATRIX.md, cases 1 and 4) already proves that
   steady-state spawns succeed reliably with ZERO code changes, because the collision
   precondition (another live process holding the shared venv's python.exe open AT THE
   EXACT MOMENT an identity mismatch is detected) does not occur in ordinary operation
   on an already-bootstrapped, unmodified install.
3. This candidate fix is recorded here, fully designed and evidence-backed, as the
   correct minimal upstream contribution for Prime if/when this race is hit again in
   practice (e.g. after a `dist/prime-agent-runtime` rebuild while sessions are live) --
   satisfying "determine the minimum safe fix" -- without being deployed against a hard
   constraint that requires this pass to stay within the previously-qualified patch set.

## Operational mitigation (zero code change, sufficient for THIS gate)

Do not modify `packages/coding-agent/dist/prime-agent-runtime` (or, when running from
source, `prime-agent-runtime/`) -- i.e. do not run a build/copy-assets step against the
live install -- while any live Prime session/kernel is attached to the shared
`~/.prime/agent/kernel-venv`. This single discipline removes the only observed trigger
for the destructive rebuild-while-in-use race on this machine.
