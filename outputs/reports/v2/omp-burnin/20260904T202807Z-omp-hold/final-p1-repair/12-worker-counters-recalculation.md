# Phase 11-16 — Worker Counters Recalculated Post-Repair

## Method

Direct per-kind scan of every `telemetry/agent-performance/*.jsonl` file in
this worktree (170 files, 169 unique session identities), counting
`omp_worker_context_handoff` (launches) and `omp_worker_child_result`
(terminal results) records — the same telemetry kinds every prior counter
report in this campaign used.

## Full-corpus totals (now, including this repair's own live-proof sessions)

| Metric | Prior recalculation (`deployment-alignment/10-phase22-final-recalculation.md`) | Now (post-repair) | Delta |
|---|---:|---:|---:|
| `omp_worker_context_handoff` (launches) | 58 | 75 | +17 |
| `omp_worker_child_result` (terminal results) | 26 (23 completed, 3 failed) | 34 (29 completed, 5 failed) | +8 (+6 completed, +2 failed) |

The +17 launches come from this repair's 3 live-proof attempts against the
real worktree home: an initial 8-worker attempt (8 launches, 0 results
captured — the orchestrator's OMP session disposed before its workers
settled, see `10-live-8worker-autodelivery-proof.md` methodology notes),
a second 8-worker attempt blocked by the budget hard cap before any spawn
(0 launches), and the successful profile-isolated 8-worker run (8 launches,
8 results). The +8 terminal results are entirely from that one successful
run — 8/8 captured purely via the repaired `message_end`/`async-result`
auto-delivery observer, zero `hub` polling (full detail and telemetry
excerpt in `10-live-8worker-autodelivery-proof.md`).

## What this proves vs. does not prove

- **Proves:** the repaired code path (`recordAsyncResultDeliveries` +
  `takePendingWorkerJob`) is live, deployed at the real OMP auto-discovery
  path, and correctly converts real auto-delivered worker completions into
  `omp_worker_child_result` telemetry that the pre-repair code would have
  silently dropped (the exact defect in
  `deployment-alignment/09-worker-result-undercount-defect.md`).
- **Does not retroactively fix historical undercounts:** the pre-repair
  portion of the corpus (the 58 launches / 26 results baseline, including
  the known "3 of 20" and "2 of 5" undercounted historical batches) was
  generated by the pre-repair extension build and cannot recover missing
  telemetry after the fact — those sessions' true completion counts remain
  documented as a lower bound in `09-worker-result-undercount-defect.md`,
  unchanged by this repair. Only NEW activity generated with the repaired
  build (this repair's own 8-worker run) demonstrates the fix.
- **Phase 22 gate status is unaffected by this recalculation**: the
  minimum-coverage gates were already re-evaluated against the fuller
  corpus in `10-phase22-final-recalculation.md` (all 10 PASS) prior to this
  repair; `RELEASE_DECISION.md`'s HOLD cites a narrower, later
  `22-sustained-burn-in/` measurement window and unrelated Phase 23 provider
  quota, not the launch/result counts recalculated here. See
  `17-Re-evaluate P0 P1 defect gate` for this repair's own P0/P1 gate
  re-assessment.
