# Deliverable 2 — 11 Questions

**1. Where exactly does AutoInject enter OMP context?**
Through the `before_agent_start` handler (`brainstem/prime-extension/src/index.ts:1291`). In shadow mode it calls `void runShadowAutoInject(autoinjectCall(session, event, ctx))` (index.ts:1420, fire-and-forget, never returns a value). In advisory/active mode it calls `aiMessage = await runAdvisoryAutoInject(autoinjectCall(session, event, ctx))` (index.ts:1382), and that `aiMessage` is merged into the handler's return value via `mergeActiveStateMessage`/`withMessage` and ultimately returned to the host as `withMessage({systemPrompt: patched}, turnMessage)` at index.ts:1608/1610, where `turnMessage` was seeded from `aiMessage` at index.ts:1598 (`let turnMessage: unknown = mergeActiveStateMessage(aiMessage, activeMessage);`).

**2. Is AutoInject only computed/telemetried, or is its packet actually inserted?**
Both, mode-dependent. In `shadow` mode (the documented default, `AutoInjectMode = "shadow"`, autoinject.ts:44) the packet is computed and recorded via `autoinjectShadowDecision` telemetry only — `runShadowAutoInject` never returns a value into the return path (index.ts:1420, `void runShadowAutoInject(...)`), matching the module doc comment autoinject.ts:5-8 ("NEVER returns a packet/patch in shadow mode"). In `advisory`/`active` mode (`aiCfg.mode === "advisory" || aiCfg.mode === "active"`, index.ts:1379), `runAdvisoryAutoInject`'s result IS inserted: it becomes part of `turnMessage`, which is returned via `withMessage(...)` at index.ts:1610 as a real `role:"custom"` `brain.autoinject.packet` message (customType constant `AUTOINJECT_CUSTOM_TYPE = "brain.autoinject.packet"`, autoinject.ts:41) — this is a genuine host-visible message, not merely telemetry.

**3. Which OMP event creates the worker capsule?**
`tool_call` (index.ts:2155), specifically when `event.toolName === "task"` (index.ts:2211). The handler `prepareWorkerTaskInput` (index.ts:614) calls `safeWorkerContextRunner` → `runOmpWorkerContext` (worker-context-bridge.ts:170), which invokes `python -m second_brain autoinject omp-routing` with `operation: "worker_context"`. Python-side, `omp_adapter.handle_request` routes to `_prepare_worker_context` (omp_adapter.py:49), which builds a `contracts.WorkerTaskPacket`, calls `worker_protocol.prepare_context_handoff(home, packet, host="omp")` and `worker_protocol.register_task(...)`, i.e. the capsule is created by Python `worker_protocol`, triggered by the TS `tool_call` interception.

**4. Which event records worker completion?**
`tool_result` (index.ts:2269), when `event.toolName === "task"` (index.ts:2367-2368). `recordWorkerChildResults` (index.ts:718) parses each result's `[SECOND_BRAIN_WORKER_TASK task_id=... packet_sha256=...]` marker, derives status, appends local telemetry (`omp_worker_child_result`, index.ts:735) and mirror (`worker_completed`, index.ts:736), then calls `workerResultRunner` → `runOmpWorkerResult` (worker-result-bridge.ts:106) with `operation: "worker_result"`, which Python-side hits `_prepare_worker_result` (omp_adapter.py:300) → `worker_protocol.record_worker_event(home, result.task_id, packet_sha256, result.status, ...)`.

**5. Which event invokes model routing?**
`before_agent_start` triggers the routing decision computation: `ensureRoutingDecision(session, task, ctx, role)` is called at index.ts:1486 (inside the `before_agent_start` handler body), which calls `routingRunner(...)` = `runOmpRouting` (routing-bridge.ts:189) → `omp_adapter.handle_request`'s default branch (omp_adapter.py, the final `task = _text(payload.get("task"), ...)` block, no `operation` key matched) → `model_routing.route_model(...)` (model_routing.py). The decision is cached (`latestRoutingDecision`) and consumed later by `before_provider_request` (index.ts:1845) to potentially swap provider/model fields on the outgoing request.

**6. Which event exposes skills/visibility?**
`before_agent_start`: `ensureVisibilityPlan(session, taskText, ctx)` is called at index.ts:1429, calling `visibilityRunner` = `runOmpVisibility` (visibility-bridge.ts:189) → `omp_adapter.handle_request` with `operation: "skill_visibility"` → `_prepare_skill_visibility` (omp_adapter.py:141) → `skills.build_plan`/`skills.hydrate_plan`. If the returned plan's `mode === "enforced"` and `hydrated_instructions` is non-empty (index.ts:1430-1432), the hydrated skill text is merged into the returned message/systemPrompt for that turn.

**7. Which events persist project/session attribution?**
`session_start` is the first mirrored event and the one the code explicitly calls out for this purpose: comment index.ts:1071-1074, "Project attribution: session_started is the first mirrored event, so the auto-init of the session ledger receives the host cwd", specifically resolving project_id via the AutoInject project-resolution ladder" (index.ts:1071-1074). The mirror call `mirror(session, "session_started", {...}, { agentId: modelId, cwd: ctxCwd(ctx) })` at index.ts:1054-1074 carries `cwd` through to `mirrorFireAndForget` → ledger-mirror.ts, which resolves project_id from cwd. Every subsequent event that calls `resolveSessionId(ctx, anonSession)` (index.ts:242, invoked in effectively every handler via `safeHandler`/`wire`) re-derives the SAME session id from `ctx.sessionManager.getSessionFile()`'s stem, so session attribution persists across `before_agent_start`, `context`, `tool_call`, `tool_result`, `turn_end`, etc. Project id specifically is re-resolved per-turn via `resolvedProjectIdForSession(session) ?? resolveProject()` (autoinject.ts, called at index.ts:1533 for PREFIX assembly and index.ts:1584 for prefix extras) and via `projectIdForCwd(ctx.cwd)` (index.ts:611) for worker dispatch — i.e. project attribution is persisted/re-derived on `session_start`, `before_agent_start`, and `tool_call` (worker dispatch).

**8. Which events support pre/post-compaction continuity?**
`session_before_compact` (index.ts:2514, registered directly not via `wire()` "so the handler can await", comment index.ts:2513) calls `runVmemCompactPrep` (vmem.ts:75, spawning `python -m second_brain vmem compact-prep <session> --json`) BEFORE compaction happens, recording what VMem would evict/preserve at the boundary (telemetry kind `"vmem_compact_prep"`, sensors.ts:670, fields `evicted_at_compaction`/`pinned_preserved`) and marks `sessionBeforeCompactOccurred.add(session)`. `session_compact` (index.ts:2607) fires AFTER compaction completes: it calls `mirror(session, "compaction_completed", ...)` (index.ts:2608) and records telemetry kind `"session_compact"` (sensors.ts:635, field `from_extension` distinguishes whether Prime or the extension itself triggered compaction). Ledger continuity across the boundary is additionally handled by `runLedgerSegmentRollover` (ledger-mirror.ts:411, `second_brain ledger segment open <session> --reason compact`), and `runLedgerCheckpoint` (ledger-mirror.ts:362) is available for checkpointing. Together: `session_before_compact` = pre-boundary VMem snapshot/preserve decision; `session_compact` = post-boundary ledger segment rollover + completion record. No dedicated "post-compaction restore" event exists beyond this pair — continuity across a resumed/compacted session otherwise relies on `resolveSessionId` (index.ts:242) re-deriving the same session id from the persisted session file stem on every subsequent event.

**9. Does any path shell out to a Prime executable?**
No. Every `execFile`/`execFileSync` call site across `brainstem/prime-extension/src/*.ts` (active-state-mirror.ts:1,133,139; autoinject.ts:22,455; budget-bridge.ts:6,68; environment-mirror.ts:1,86; index.ts:44,357; ledger-mirror.ts:18,163,170,229,266,362,411; p4-mirror.ts:6,86,124; recall-gate.ts:35,230; routing-bridge.ts:3,189; rtd.ts:31,494; visibility-bridge.ts:3,189; vmem.ts:34,75,173,226,318,396,464,504,566; worker-context-bridge.ts:3,170; worker-result-bridge.ts:3,106) invokes `python` — resolved as `options.python ?? process.env.SECOND_BRAIN_PYTHON ?? join(home, ".venv", "Scripts", "python.exe")` (this exact pattern repeats in every bridge file, e.g. routing-bridge.ts:157, visibility-bridge.ts:167, worker-context-bridge.ts:143) — running `-m second_brain <subcommand>`. A grep for `spawn\(|execFile|execSync|exec\(` across the whole `src/` tree returned zero references to `prime`, `prime-agent`, `prime.exe`, `sol`, or any Prime-branded binary; the only executable ever launched by this extension is the local Python interpreter.

**10. Does any required path import Prime-specific types only, versus requiring a Prime runtime at execution time? Distinguish compile-time type-only imports from runtime dependencies.**
`index.ts:28-41` imports `AgentEndEvent, BeforeAgentStartEvent, ExtensionAPI, ExtensionContext, PrimeEvent, SessionBeforeCompactEvent, SessionCompactEvent, SessionShutdownEvent, SessionStartEvent, ToolCallEvent, ToolCallEventResult, ToolResultEvent, TurnEndEvent, TurnStartEvent` via `import type {...} from "../types/prime"` — the `import type` keyword makes this a TypeScript compile-time-only import (erased entirely by the Bun/TS compiler, produces zero runtime code, zero runtime dependency on any Prime module or binary). No other file in `brainstem/prime-extension/src/` imports from `../types/prime` at all (confirmed: `index.ts` is the sole consumer of that type-declaration file). At runtime, the ONLY thing the extension needs from "Prime" is the `pi`/`ExtensionAPI` object the OMP host injects into the factory function it calls (`export default function(pi: ExtensionAPI, options?: ...) {...}` pattern) — this is duck-typed (`pi.on(...)`, structural), not a Prime-specific class/runtime import. Every actual runtime dependency in the extension is on Node/Bun builtins (`node:child_process`, `node:fs`, `node:crypto`, `node:sqlite`, `node:path`) plus the local Python `second_brain` package — never a Prime package.

**11. Can all required OMP behavior execute when no Prime binary exists? State yes/no per capability.**
- **AutoInject**: YES. `runShadowAutoInject`/`runAdvisoryAutoInject` (autoinject.ts) spawn only `python -m second_brain autoinject shadow|advisory` (verified contract comment autoinject.ts:15-19); the OMP host process itself provides the `pi.on("before_agent_start", ...)` hook and message-return contract, with no Prime binary invoked anywhere in the call chain.
- **Routing**: YES. `runOmpRouting` (routing-bridge.ts:189) spawns only `python -m second_brain autoinject omp-routing`; the Python side (`model_routing.py`) is a pure, harness-neutral module per its own docstring ("does not... know how a host invokes a provider", model_routing.py:14-16) with zero Prime imports.
- **Worker context**: YES. `runOmpWorkerContext` (worker-context-bridge.ts:170) spawns only `python -m second_brain autoinject omp-routing` with `operation:"worker_context"`; capsule creation happens entirely in `worker_protocol.py`/`contracts.py`, invoked from the generic `tool_call` OMP hook (a host-provided built-in `task` tool, not a Prime-specific API).
- **Worker result**: YES. `runOmpWorkerResult` (worker-result-bridge.ts:106) likewise spawns only Python; recorded via the generic `tool_result` hook.
- **Visibility**: YES. `runOmpVisibility` (visibility-bridge.ts:189) spawns only Python with `operation:"skill_visibility"`; `skills.py` build_plan/hydrate_plan has no Prime dependency.

Overall: every one of these five capabilities' runtime dependency graph terminates at (a) Node/Bun builtins, (b) the local Python venv running `second_brain`, and (c) the OMP host's own generic `ExtensionAPI`/lifecycle-event contract (which this audit's live testing already confirmed works standalone via `omp -e ./brainstem/prime-extension/src/index.ts` with no Prime binary present on the machine). None require a Prime executable at any point.
