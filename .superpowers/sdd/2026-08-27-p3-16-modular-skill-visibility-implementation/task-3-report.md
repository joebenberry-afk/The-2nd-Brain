## Post-review fix: `active_state`/`visibility` details-key collision (P2)

**Finding (from `Main`'s review):** the original visibility injection routed its merge through `mergeActiveStateMessage(aiMessage, {content, details: {visibility_plan_id}})`. That helper hardcodes the second argument's `details` under a literal `active_state` key (its only prior caller merges the real active-state capsule). Every `before_agent_start` return path then re-runs `mergeActiveStateMessage(aiMessage, activeMessage)` at the end, which unconditionally **overwrites** `details.active_state` with the real active-state capsule's own details — silently discarding `visibility_plan_id` whenever AutoInject mode ("advisory"/"active"), active-state mode, and an enforced visibility plan with hydrated content all coincide (realistic, since AutoInject and active-state both gate on the same `aiCfg.mode`). The injected specialist *text* survived; only the `visibility_plan_id` correlator was lost.

**Fix:** added a dedicated `mergeVisibilityMessage(primary, specialistText, visibilityPlanId)` helper in `src/index.ts` (placed immediately after `mergeActiveStateMessage`, same file, same section) that merges the specialist text under its own `details.visibility.visibility_plan_id` key instead of borrowing `mergeActiveStateMessage`'s `active_state` slot. Its branching mirrors `mergeActiveStateMessage`'s own fail-open semantics (no existing message → return the new one; existing message without a string `.content` → return it unchanged; otherwise concatenate content and merge details). The `before_agent_start` visibility-injection call site now calls `mergeVisibilityMessage(aiMessage, specialistText, visibilityResult.visibility_plan.visibility_plan_id)` in place of the old `mergeActiveStateMessage(aiMessage, {content, details})` call. Because `visibility` and `active_state` are now distinct `details` keys, the later `mergeActiveStateMessage(aiMessage, activeMessage)` call's `{...primaryDetails, active_state: activeDetails}` spread preserves `details.visibility` untouched.

**Regression test:** added `active-state-wiring.test.ts` > *"merging an enforced-mode visibility injection with a live active-state capsule preserves both (regression: visibility_plan_id must survive the active_state merge)"*. This required also mocking `runAdvisoryAutoInject` in that file (added `runAdvisoryAutoInjectMock`, default `mockResolvedValue(undefined)` — matches its real fail-open behavior in a venv-less test home, so the file's pre-existing test is unaffected) so the test can give `aiMessage` real string content (`"AUTOINJECT PACKET TEXT"`) from AutoInject mode `"active"` (already the file's default config), combined with the file's existing real active-state capsule mock (`messageMock`) and a new `runOmpVisibilityMock` enforced-plan resolution. The test asserts the final message's `content` contains both `"AUTOINJECT PACKET TEXT"` and `"specialist body text"` and the real active-state marker, and that `details.visibility.visibility_plan_id === "vplan-collision-1"` **and** `details.active_state` still equals the real active-state details — i.e. both merges' payloads survive together. Before the fix this test fails (`visibility_plan_id` is `undefined`, having been overwritten); after the fix it passes.
